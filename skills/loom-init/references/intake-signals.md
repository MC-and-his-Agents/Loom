# Intake Signals

使用本文件组织 `loom-init` 的初始化问诊。

## 1. 先判断当前场景

- 新项目
  - 目标是建立最小起步结构
- 既有仓库
  - 目标是识别结构性缺口并渐进补齐

## 2. 关键信号

### A. 审查时点

至少判断：

- 高质量语义判断是否在实现前已经发生
- 还是主要拖到 merge 前才第一次系统性发生

如果后者成立，应优先引入前移 checkpoint 与 review 分层。

### B. 长任务恢复

至少判断：

- 事项是否经常跨多轮推进
- 中断后是否需要靠聊天记录或人脑恢复
- 当前是否缺唯一恢复主入口

如果以上任一问题明显成立，应优先引入恢复模型。

### C. 共享边界与风险

至少判断：

- 是否涉及共享契约
- 是否涉及共享数据模型
- 是否涉及核心抽象或高风险链路

如果成立，应优先引入正式规约套件与 admission checkpoint。

### D. 现场纯度

至少判断：

- 是否经常一个分支混多个目标
- 是否经常一个 PR 混多个语义主题
- 是否经常在脏现场继续叠加正式事项

如果成立，应优先引入隔离现场与纯度预检。

### E. 自动化前置

至少判断：

- 是否存在高频重复、口径稳定、可结构化判断的检查
- 这些检查当前是否仍在人工 review 中反复执行

如果成立，应优先规划自动化前置。

## 3. 初始化建议的基本映射

- 只有轻量需求、低中断成本、低共享边界风险
  - 装配最小治理与基础 PR 模板
- 既有仓库已经有清晰工程边界、CI/测试基线，但缺执行入口与 review/spec 合同
  - 优先装配最小治理入口
  - 保留原有根级边界文档
  - 先不引入 recovery/work-item/status-surface
- 存在中等复杂度事项，但不总是进入正式规约
  - 增加简化设计说明与 build checkpoint
- 存在共享边界、高风险链路、长任务中断成本高
  - 增加正式规约套件、恢复模型、隔离现场与纯度规则

## 4. 来自 `mail-listener` 的确认信号

以下信号同时成立时，优先选择“最小治理包”而不是完整 Loom 装配：

- 仓库已经有清晰 `AGENTS.md` 或同类根规则文档
- 仓库已经有 CI 和基础测试
- 主要问题是“改动如何进入实现”和“review 如何判断”
- 当前还没有明显的长任务恢复痛点

这类仓库的第一轮默认输出应是：

- companion docs 接入
- 最小 `WORKFLOW`
- 最小 `code_review`
- 条件化 `spec_review`
- 基础 PR 模板
