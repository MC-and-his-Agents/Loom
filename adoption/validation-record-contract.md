# Real Adoption Validation Record Contract

本文定义 Loom 在 `Phase E` 及后续真实 adoption 验证中使用的统一记录合同。

它的目标不是生成泛化总结，而是让每次验证都能稳定回写到 `extraction-ledger.md`、`landing-map.md`、相关核心文档与 GitHub issue。

## 1. 使用边界

本合同适用于以下三类真实验证：

- 新项目验证
- 小型既有仓库复验
- 复杂既有仓库验证

每次真实验证都必须采用同一结构，不允许临时增删关键区块。

## 2. 必填区块

### 2.1 样本标识

至少写清：

- 样本仓库名
- 仓库类型
  - `新项目`
  - `小型既有仓库`
  - `复杂既有仓库`
- 仓库位置
- 验证日期
- 对应 Loom issue

### 2.2 仓库事实

至少写清：

- 根级边界文档现状
- README / 流程文档 / 模板现状
- CI、测试或等价质量基线现状
- 当前主要缺口
- 当前是否已有恢复、状态或执行支撑
- 当前是否出现共享契约、高风险边界、纯度问题或 review 过载

这里只记录样本事实，不提前写 Loom 结论。

### 2.3 `loom-init` 判断

至少写清：

- 场景判断
- 装配强度
- 推荐路径
- 为什么不是另外两条路径
- 当前恢复形态
  - `checkpoint-lite`
  - 标准恢复形态
  - 暂不引入恢复工件

### 2.4 首批装配结果

至少写清：

- 本轮启用的 Loom 能力
- 本轮暂不启用的 Loom 能力
- 首批工件与其承载位置
- 恢复主入口
- 验证入口
- 状态读取入口
- 初始 clean state 定义

### 2.5 摩擦、失效点与升级信号

至少写清：

- 当前默认路径成立的证据
- 当前默认路径失效或偏离的证据
- 哪些信号会触发升级
- 哪些宿主或仓库细节不得直接提升为 Loom 内核

### 2.6 台账回写结果

至少写清：

- 新增或修正的 `EXT-*`
- 对应 `EXT-*` 的状态变化
- `landing-map.md` 的新增或修正项
- 受影响的 Loom 核心文档

### 2.7 关闭依据

至少写清：

- 对应 issue 的完成判断是否满足
- 还有哪些部分继续留在 `adapt` 或 `needs_validation`
- 为什么可以关闭，或为什么必须继续保留开放状态

## 3. 回写规则

每次真实验证都必须遵守以下回写顺序：

1. 先写验证记录
2. 再更新 `extraction-ledger.md`
3. 再更新 `landing-map.md`
4. 再同步相关核心文档
5. 最后更新 issue 依据与关闭语义

不允许跳过台账回写，只保留一份案例记录。

## 4. 状态提升规则

- 单仓样本首次得出的新结论，默认进入 `needs_validation` 或 `adapt`
- 至少两个独立样本支持、且不依赖单一宿主细节，才能提升为 `keep`
- 若验证结果是否定，也必须回写到台账，而不是只在 issue 评论中说明
- 若结论仍不足以进入内核，必须明确其继续停留在候选区的原因

## 5. 与 issue 的关系

真实 adoption 验证记录本身不是 issue 关闭条件的替代品。

issue 只有在以下信息已对齐时才可关闭：

- 验证记录已提交
- 台账与落点已同步
- 相关核心文档已更新
- 关闭语义与当前文档真相一致
