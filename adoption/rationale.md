# Adoption Rationale

本文件定义 Loom 的采用理由与上游边界。

本文件当前承接：

- `EXT-0005`
- `EXT-0010`
- `EXT-0021`
- `EXT-0030`

## 1. 为什么要采用 Loom

Loom 的直接目标不是提供业务模板，而是把真实仓库中反复出现的运行问题，上移成可复用能力。

它重点解决：

- 治理与业务同仓带来的可演进性问题
- 长任务恢复能力缺失
- 审查职责混杂
- merge 前 review 过载

## 2. Loom 的上游边界

Loom 只沉淀多仓实证下成立的运行模型。

默认要求：

- 不复制单一仓库的完整结构
- 不绑定某个业务领域
- 不把局部历史状态误当成 Loom 默认内核

## 3. 采用 Loom 的结构性理由

### `EXT-0005`

治理与业务同仓有上下文优势，但长期会削弱治理能力独立演进。

Loom 的存在，就是把这部分能力上移成独立上游。

### `EXT-0010`

Loom 的目标是提炼运行模型，而不是复制仓库。

### `EXT-0021`

实现前审查里程碑即使在制度上存在，也必须被工程化成可执行状态。

### `EXT-0030`

merge 前 review 过载，通常不是 guardian 本身的问题，而是前移 checkpoint 没有稳定生效。

## 4. Loom 当前采用原则

采用 Loom 时，默认应同时接受：

- 上游与业务分层
- 规则与工件入库
- 前移 checkpoint
- merge gate 不承担第一次高质量语义判断
